## Verdict

**Ready with bounded clarifications.** The scoring design is coherent and the scope is appropriately limited. Before fixing the v1 serialization contract and implementing run persistence, resolve two high-priority ambiguities: how assembled predictions represent more than one originating configuration, and how evidence references survive snapshot relocation. Three smaller contract gaps also need explicit resolutions below. These do not require a broader evaluation platform.

The first two findings block the affected provenance/persistence contract, not implementation of the mathematical core. None establishes that the proposed metric formulas are wrong. Priority P1 means resolve before committing the affected public contract; P2 means resolve before claiming v1 conformance.

## Implementation blockers for the affected contracts

### 1. P1 — Assembled successive passes have no defined source-attribution contract

**Evidence:** `docs/specs/validator-v1.md`, lines 123–134 require one `source.kind`, one recorded `model`, and one opaque `configuration`. Lines 136–172 define prediction rows without an origin reference. Lines 558–562 permit a full-population artifact assembled from retained and revised outputs, require provenance for both, and correctly warn that retaining old predictions does not evaluate the revised classifier on those episodes. Lines 411–418 and 456 require source and per-episode evidence in the report. Lines 510–512 require comparison to expose source/configuration differences.

**Counterexample:** A first pass evaluates episodes A and B with scored-choice question configuration Q1. A later pass evaluates only B with revised Q2. A user explicitly assembles A-from-Q1 plus B-from-Q2, as lines 558–562 permit. Setting the envelope configuration to Q2 misattributes A; setting it to Q1 misattributes B. Attaching two raw response files does not specify a machine-readable association between each episode and its originating configuration. An opaque configuration object could encode a composite producer and an ID-to-origin mapping, but the current contract does not say that this is the meaning of `model`/`configuration` for assembled artifacts or require consumers to understand it.

**Consequence:** Two implementations or preparation agents can emit incompatible provenance for an expressly supported workflow. A machine consumer can mistake an assembled result for evidence about one revised classifier on the whole population, despite the prose warning. This is an ambiguity, not a claim that heterogeneous predictions are mathematically unscorable or that opaque evidence can never document their origins.

**Smallest correction or decision:** Decide whether v1 permits assemblies whose originating model or question configuration differs. If not, explicitly restrict assembly to a homogeneous declared source and require a fresh complete evaluation for a changed classifier. If it does, define a minimal structured origin association for retained/revised episode IDs and state how the envelope identifies the composite result. Reuse source artifacts/run identifiers and their digests where possible; no automatic merge engine is needed. A documented composite-producer convention is an alternative only if the machine contract makes the heterogeneous origin visible and unambiguous.

**Acceptance check:** Construct the two-episode Q1/Q2 example. It must either fail with the declared homogeneous-source restriction, or produce a report from which an agent can identify A's Q1 origin and B's Q2 origin without parsing prose or guessing from filenames. Comparison must not describe the entire assembled population as having been generated by Q2.

### 2. P1 — Exact prediction snapshots retain evidence paths that are invalid during replay

**Evidence:** `docs/specs/validator-v1.md`, lines 126–129 make evidence paths relative to the prediction file and require them to exist. Lines 398–401 require exact prediction bytes but relocate evidence into uniquely named files under `evidence/`. Line 456 replaces evidence paths in the report's `source` with stored artifact references. Lines 485–490 require digest verification and recomputation using snapshots and prohibit following snapshot paths outside the run.

**Counterexample:** `/work/predictions.json` contains `source.evidence: ["raw/answer.json"]`. Evaluation stores those exact prediction bytes as `run/predictions.json`, but the attached evidence becomes `run/evidence/0001.json`. Once the original working directory is unavailable, revalidating the prediction snapshot using the original path rule looks for `run/raw/answer.json`, which does not exist. An original `../raw/answer.json` reference would also collide with replay's containment requirement. Rewriting the prediction snapshot to the stored name would violate the exact-byte requirement and change its digest.

**Consequence:** A straightforward reuse of input validation during inspection/comparison fails for otherwise valid, self-contained runs. The report's rewritten source suggests the intended solution, but the specification does not require a binding from each original evidence reference to its stored artifact or state which resolver governs replay. Different implementations may depend on external files, skip evidence checks, or associate the wrong evidence when filenames collide.

**Smallest correction:** Make the replay resolution rule explicit: preserve the submitted bytes; record a deterministic binding from each source evidence entry, such as its array index and original path, to the copied artifact path and digest; and resolve snapshot validation through that binding exclusively. Define missing, duplicate, or inconsistent bindings as integrity errors. Containment checks apply to stored artifact paths, while original source paths remain provenance strings and are never dereferenced during replay. This completes the existing snapshot design.

**Acceptance check:** Evaluate with two evidence files sharing a basename in different source directories, including a relative parent-directory reference. Copy the run to an unrelated directory and make the original sources unavailable. Inspection and comparison must succeed using only the run contents. Swapping a binding, changing an evidence byte, or making a stored path escape through a symlink must fail without consulting the originals.

## Lesser contract gaps

### 3. P2 — Empty comparison signal statuses conflict with applicability precedence

**Evidence:** `docs/specs/validator-v1.md`, lines 169–172 say empty prediction artifacts contain neither signal family. Lines 324–329 distinguish `no_data` from `not_applicable` and require applicability to be determined first. Lines 515–519 say an empty intersection has `no_data` metrics. Lines 525–527 make statuses control whether comparison deltas exist.

**Counterexample:** Compare two nonempty, label-only runs on disjoint selections using `--intersection`. The compared population is empty. Probability metrics should be `not_applicable` under the absent-signal rule, but the unconditional empty-intersection sentence says `no_data`. For two probability-bearing runs, it is also unstated whether recomputation retains each source run's signal availability or treats the empty restriction like an empty prediction artifact, which would erase availability.

**Consequence:** Agent-visible status and delta reasons depend on which paragraph the implementation follows. Empty intersections are expressly valid, so this is part of ordinary behavior rather than an unsupported corner case.

**Smallest correction:** State that comparison retains each source run's signal applicability when restricting its population. Applicable families become `no_data` on an empty intersection; absent families remain `not_applicable`. Clarify that “empty artifacts contain neither signal family” describes newly supplied prediction artifacts, not restrictions of an existing run. If another policy is intended, specify its precedence equally explicitly.

**Acceptance check:** Cover empty intersections for probability/probability, label-only/label-only, and probability/label-only sources. Assert both sides' exact statuses and the null-delta reasons, alongside `no_data` hard-decision metrics. Also cover a directly evaluated empty artifact, whose signal families are absent under the current input contract.

### 4. P2 — The unresolved-reference rejection claim exceeds the observable data

**Evidence:** `docs/specs/validator-v1.md`, lines 87–99 provide only a scalar expected class and opaque input, without settlement/review metadata. Lines 105–110 allow `UNCERTAIN` as a settled ordinary class but conclude: “Validator rejects unresolved labels in submitted gold.” Lines 50–52 correctly assign reference correctness to the dataset owner, and lines 573–580 assign withholding records to preparation evidence that can optionally be attached.

**Counterexample:** Two canonical episodes have identical structure and `expected: "UNCERTAIN"`, where that class is declared. One is a settled domain judgment; the other is a preparer's unresolved placeholder. Both satisfy the entire observable schema. Similarly, an unresolved disagreement can be serialized as a valid class A. Validator cannot distinguish these cases without interpreting external review evidence or inventing domain semantics, neither of which v1 authorizes.

**Consequence:** The current sentence can lead an implementer to reject a legitimate class name or an agent to treat a successful check as evidence that all references were settled. The contract otherwise correctly avoids that promise.

**Smallest correction:** Narrow the claim to what Validator observes: it rejects missing, null, non-scalar, or undeclared expected labels; source preparation is responsible for excluding unresolved references even when they could be encoded as legal class strings. State that successful validation does not attest to settlement. No new adjudication field or input schema is needed.

**Acceptance check:** A settled, declared `UNCERTAIN` class is accepted. Missing/null/undeclared references fail structurally. A legal class string cannot receive a special unresolved-reference rejection merely from its spelling or opaque payload, and the documented check guarantees do not imply review-status verification.

### 5. P2 — Receipt digest target is undefined

**Evidence:** `docs/specs/validator-v1.md`, lines 442–443 require a receipt with an absolute “artifact path” and “artifact SHA-256.” Lines 384–385 and 474–477 publish directories. Lines 480–483 define exact-byte hashes and refer to a manifest, but there is no directory hashing algorithm. Lines 521–523 explicitly use the source runs' report-file digests in comparisons.

**Counterexample:** `evaluate --out runs/001` succeeds. One implementation returns the absolute directory path plus the SHA-256 of `report.json`; another returns the report-file path; a third hashes an ordered concatenation of the directory's files. All can plausibly interpret “artifact,” yet a consumer cannot reliably verify the receipt from the specification. A SHA-256 of a directory has no inherent byte representation.

**Consequence:** The public machine interface is ambiguous at the point where an agent locates and verifies the result. This is especially avoidable because the report already contains the component file hashes.

**Smallest correction:** Specify that the receipt identifies the exact result file (`report.json` or `comparison.json`) and hashes its bytes. If the directory path is also required, give it a separate field. Identify the run report's artifact list as the manifest if that is the intended usage; do not add an unnecessary recursive-directory hashing scheme.

**Acceptance check:** For each receipt type, independently open the named result file, hash its exact bytes, and match the returned digest. A consumer must not infer an extra filename or directory encoding from prose.

## Load-bearing product choices to ratify explicitly

These are coherent design choices, not additional defects. The session notes call the specification a proposal and do not establish that every authoring choice has been accepted.

- **Mixed abstention and signals:** Lines 166–172 jointly mean that one explicit abstention forces every class row in that artifact to omit probabilities and confidence. A classifier that supplies distributions for answered rows and abstains on another cannot preserve all those signals in one accepted artifact. Keep the rule if the intended tradeoff is simpler, population-complete diagnostics; do not relax it accidentally while implementing optional fields.
- **All-or-nothing run validity:** Lines 215–230 reject missing outputs, extra outputs, partially supplied signals, and threshold policies applied to explicit abstentions. There is no partial-success report for inference failures. That preserves denominator integrity but must match the intended producer workflow.
- **Exact-byte dataset identity and reference revision exclusion:** Lines 480–483 and 510–513 deliberately reject comparison after mere golden-file reformatting or a reference revision, even when selected records happen to be unchanged. This is strict and simple; it is not a hash defect and does not require semantic hashing.
- **Fixed-schema macro-F1:** Lines 323 and 330–333 zero-fill missing class F1 terms only inside macro-F1 and mark the result `contains_undefined_classes`. Lines 525–527 consequently suppress its numeric comparison delta even when both macro-F1 values are finite. This is internally consistent; confirm that the reduced delta availability is intended for sparse conflict selections.
- **Saved-output evaluation and manual preparation:** The CLI never invokes a classifier and never automatically inherits prior predictions. Preparation supplies UUID stability and trustworthy source mappings. This is a material boundary, not an implementation omission.
- **No inference or acceptance gates:** Fixed bins, no intervals, and no winner/release verdict are explicit scope choices. The review does not recommend importing the master specification's broader capabilities.

## Correct choices and verified evidence

The distinction between recorded choice, probability distribution, vendor confidence, thresholded final outcome, and empirical correctness is well designed. Current official [TypeSafe Choice documentation](https://docs.typesafe.ai/primitives/choice) describes selection of a maximum-probability option, complete keyed probabilities, and separate confidence. Its example includes a 0.60 maximum probability and 0.39 confidence. The [TypeSafe confidence documentation](https://docs.typesafe.ai/confidence) describes confidence as a statistic of distribution shape and makes threshold interpretation task-dependent. These sources support the v1 mapping; this review found no reason to substitute maximum probability for returned confidence or to reimplement the vendor formula. The Choice page's official Markdown endpoint was successfully retrieved after the web reader returned a service error.

Hard-decision accounting is consistent: wrong class decisions contribute one global error, while abstentions contribute false negatives but no class false positives. The fixture at line 595 has class F1 values `1/2`, `0`, and `1`, hence macro-F1 `1/2`. The adopted [master F04 fixture](../../multi_class_classification_validation_specs.md), lines 753–782, yields F1 values `4/7`, `4/5`, and `1/2`; their mean is `131/210`, and accuracy is `5/8`. The Brier fixtures at lines 599–600 also match the stated unscaled multiclass formula.

Typed abstention columns, explicit selection, ID-based alignment, exact snapshots, raw/final separation, unrejected probability populations, and paired intersection recomputation should be preserved. The warnings about targeted populations, repeated observations, and unverified `held_out` claims correctly constrain interpretation without adding an evaluation platform.

## Optional implementation guidance

No optional product capability is recommended. When finalizing the already-required schemas, define the precision used to parse numeric scoring fields and perform normalization. “At least binary64” (lines 251–262) allows different working precision near exact threshold boundaries; recording a concrete numerical convention will make replay compatibility easier to judge. Opaque JSON payloads also need value-preserving handling during inspection, including large integers. These are implementation-design checks, not evidence that a defect currently exists in code.

The published schemas are explicitly an implementation deliverable, so their absence from this proposed document is not separately counted as a finding. The five findings above identify semantic decisions those schemas cannot safely settle by arbitrary field naming.
